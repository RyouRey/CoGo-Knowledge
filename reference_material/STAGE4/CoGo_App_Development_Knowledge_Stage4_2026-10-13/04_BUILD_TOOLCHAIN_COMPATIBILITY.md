# Build Toolchain and Compatibility in CoGo

## Snapshot facts

Official CoGo release notes identify 26.41 (2026-10-06) as current in the 2026-10-13 research snapshot. The official modernization article says release 26.38 introduced the upgraded stack, with Kotlin 2.3.21, AGP 9.3.1, Gradle 9.6.1, and Build Tools 36.0.0 for updated templates. TOML version catalogs are optional.

Projects created on CoGo 26.37 or earlier can fail after upgrading CoGo to 26.38+ until migrated. Projects created by the updated templates should already be configured for the new stack.

## Always inspect before changing

For an existing project, check:

1. Root `build.gradle` / `build.gradle.kts`.
2. `app/build.gradle` / `app/build.gradle.kts`.
3. `gradle/wrapper/gradle-wrapper.properties`.
4. `gradle/libs.versions.toml`, if present.
5. `gradle.properties`, manifest, `compileSdk`, `minSdk`, Java/Kotlin compiler settings.
6. The exact first failure in CoGo Build Output, not just the final failure summary.
7. CoGo release and CPU architecture if relevant.

## Safe approach for a new project

Use the template generated by the installed CoGo version. Avoid manually replacing AGP, Gradle, Kotlin, SDK, and plugin versions with the latest internet examples. First build the untouched template. Then add one feature/dependency at a time and build again.

## Migration for projects created before 26.38

The official CoGo wiki has two cases based on whether `gradle/libs.versions.toml` exists. It documents updating AGP to 9.3.1, adding a root `buildscript` classpath for Kotlin Gradle plugin 2.3.21, removing the Kotlin Android plugin line from the app module (AGP 9 compiles Kotlin itself in this stack), updating old `kotlinOptions` target syntax where applicable, and removing forced old Kotlin stdlib versions. The precise edit depends on project shape.

**Do not blindly paste migration steps into every project.** The official guide says to first open the project and try building; if it already builds, no migration is needed. Back up or commit before edits. Follow the exact current official guide:
https://github.com/appdevforall/CodeOnTheGo/wiki/IMPORTANT:-Fix-project-breaking-changes-after-the-Gradle-AGP-Kotlin-toolchain-upgrade

## Offline mode and dependencies

CoGo is offline-capable, but not every third-party dependency or plugin version is guaranteed to exist in the local cache. If a dependency isn't cached, build resolution may need internet. The migration guide notes that disabling `--offline` in Preferences → Build & Run → Additional Gradle flags allows Gradle to download versions it needs. Do this only when connectivity/data policy allows; don't imply offline builds can fetch uncached artifacts.

## Version catalogs

If `gradle/libs.versions.toml` exists and the build uses aliases, preserve that pattern. Example pattern:

```toml
[versions]
exampleLib = "1.2.3"

[libraries]
example-lib = { module = "com.example:library", version.ref = "exampleLib" }
```

Then use the matching generated alias in the module build file. The alias name is derived from the catalog key; inspect the project before inventing it. Adding a catalog is optional and should not be required just to use the upgraded toolchain.

## DSL compatibility

- `build.gradle` usually means Groovy DSL.
- `build.gradle.kts` means Kotlin DSL.
- The same setting often has different syntax in the two DSLs.
- A Kotlin app source file does not prove that Gradle uses Kotlin DSL.

## Compatibility decision tree

- Fresh template builds? Keep its versions; proceed.
- Existing project builds? Don't migrate unnecessarily.
- Existing project from 26.37 or earlier fails after CoGo update? Back up; identify catalog/no-catalog case; follow official migration guide.
- `org.jetbrains.kotlin.android plugin is no longer required`? In the new AGP 9.3.1 stack, check for the obsolete Kotlin Android plugin line as documented.
- `Using kotlinOptions is an error`? Inspect old Kotlin target configuration and follow migration instructions.
- Unknown compatibility error? Capture the full first error, toolchain versions, and relevant build files; don't mass-upgrade dependencies.
