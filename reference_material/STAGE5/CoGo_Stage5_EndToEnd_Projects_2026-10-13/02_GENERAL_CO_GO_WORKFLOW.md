# General workflow: blank project to tested APK

## A. Before creating the project
Record:
- CoGo version (Settings/About or app info).
- Android version, device model, CPU architecture if known.
- Free storage and available memory.
- Whether the project is new or migrated from an older CoGo version.
- Whether network access is available. CoGo is designed for on-device/offline development, but first-time dependency resolution and some dependencies can still depend on what's already cached/available.

## B. Create a project
1. Open CoGo and choose New Project.
2. Choose the simplest template that matches the app architecture:
   - Java + XML: a Java/View template.
   - Kotlin + XML: a Kotlin/View template.
   - Kotlin + Compose: a Compose template that actually creates the Compose dependencies and setup.
3. Enter a project name such as `UnitConverter`, `QuickNotes`, or `ComposeCounter`.
4. Use a valid reverse-domain package name such as `com.example.unitconverter` (lowercase identifiers; no hyphens). If CoGo derives a package from the project name, inspect and correct it before creating the project.
5. Keep SDK and build-tool defaults generated by the installed CoGo version unless a requirement demands a change.
6. Finish project creation and wait for initial Gradle sync/build to settle. Do not start debugging a source-code issue while sync is still running.

## C. Inspect the generated structure
Common Android application paths (confirm in the actual project tree):
- `app/src/main/AndroidManifest.xml` — app components, permissions, application metadata.
- `app/src/main/java/<package>/MainActivity.kt` or `.java` — Activity code; exact package path varies.
- `app/src/main/res/layout/activity_main.xml` — XML View layout, only if the template uses XML.
- `app/src/main/res/values/strings.xml` — user-visible strings.
- `app/src/main/res/drawable/` — drawable resources.
- `app/build.gradle.kts` or `app/build.gradle` — app-module configuration; do not assume Kotlin DSL in every project.
- Root `build.gradle(.kts)`, `settings.gradle(.kts)`, and version catalog — project-wide build configuration; preserve template-generated versions.

## D. Change one thing at a time
1. Make a backup or commit a baseline before broad edits.
2. Apply the code changes listed by the blueprint.
3. Confirm package declarations match the real generated package.
4. Confirm resource IDs in code match XML IDs exactly.
5. Save all files.
6. Sync/build and read the first meaningful error, not just the final `BUILD FAILED` line.
7. Fix one root cause, rebuild, and record whether the error changed.

## E. Build and run
1. Start with the normal Gradle build/run flow supplied by the current CoGo version.
2. Select the `debug` variant for development.
3. Wait for the task to finish. A successful compile is not yet a successful runtime test.
4. Install/launch and manually exercise the app.
5. If Quick Build is enabled, treat it as an iteration accelerator only after the normal project can build and run. Confirm every edit either reloads or visibly falls back to a normal build.
6. Before distributing an APK, build a release variant and handle signing securely. Never paste passwords or keystore secrets into chats or source control.

## F. Capture useful evidence
Record the exact project template, CoGo version, package name, device, build task, build output, install/launch outcome, test steps, screenshots if useful, and the changed files. A vague statement such as “it doesn't work” is not enough to diagnose a project-specific problem.
